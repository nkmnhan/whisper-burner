# whisper-burner Instructions

## Project Purpose
Batch video transcription & subtitle burning using OpenAI Whisper in Docker. Processes videos from `videos/` into SRT transcripts and MP4s with burnt-in subtitles, saved to `videos/output/`. Supports both GPU and CPU execution profiles.

## Architecture Overview
- **Dockerfile** — Python 3.12-slim base with ffmpeg + openai-whisper
- **docker-compose.yml** — Two profiles: `gpu` (default) and `cpu`
- **process-videos.ps1** — Core PowerShell orchestrator for batch operations
- **Launchers** — `process-videos-gpu.cmd` / `process-videos-cpu.cmd` (double-click friendly)
- **Model storage** — `models/` directory persisted via Docker volume
- **Input/output** — `videos/` for sources; `videos/output/` for generated files

### Current Architecture
- Target: `net9.0-windows10.0.22621.0`, unpackaged, x64 only
- Settings file: `~/whisper.live/settings.json`
- Sessions directory: `~/whisper.live/sessions/`
- `App.xaml.cs` owns service singletons, caches `_currentSettings`, applies updates through `ApplySettings()`, constructs `SessionAssistantService(RecordingManager, aiProvider, () => _currentSettings)`, and creates `CaptionOverlayWindow`
- `MainWindow` provides the `MicaBackdrop` + `TitleBar` + `NavigationView` shell for `LiveTranscriptPage`, `SessionsPage`, and `SettingsPage`
- Recording flow: `LiveTranscriptPage` → `RecordingManager` → `RecordingService` → `TranscriptionClient` → `SubtitleService` → `TranslationService` → `TranscriptViewModel` → `CaptionOverlayWindow`

### Key Architectural Rules
- `ISrtSessionWriter` is the required abstraction for all session SRT streaming writes. `SubtitleService` and `TranslationService` must use `StreamingSrtWriter` via this interface — never create a raw `StreamWriter` for SRT output
- `SessionAssistantService` receives `Func<AppSettings>` from `App`. Never call `AppSettings.LoadAsync()` inside assistant service methods; always use the injected getter
- Segoe MDL2 Assets glyphs in C# must always use escaped `"\uXXXX"` sequences, never pasted raw Unicode. Verified glyphs include `\uE768`, `\uE769`, `\uE70D`, `\uE70E`, `\uE711`
- `SessionsPage` must read SRT files with `FileShare.ReadWrite` so live-written session files can be opened during active recording/translation

### Key Conventions
- Services are singletons on `App`; pages access them via `((App)Application.Current).ServiceName`
- Background service events that update UI must marshal with `DispatcherQueue.TryEnqueue(() => ...)`; keep dispatching in the presentation layer, not the services
- Use `AppLogger` for production logging (`Info`, `Warning`, `Error`)
- Call `WindowHelper.TrackWindow(this)` in every `Window` constructor
- Put custom brushes only in `Styles/Brushes.xaml` `ThemeDictionaries`
- Settings UI uses `SettingsCard` / `SettingsExpander`, not raw `Expander`
- Add CsWin32 APIs to `NativeMethods.txt`; use `[DllImport]` only when CsWin32 does not cover the interop
- Use one `CancellationTokenSource` per recording session; cancel on stop and page unload
- Keep one type per file; interface and model files should stay small
- No UI logic directly in `Page`/`Window` — delegate to services or view models

## Coding Conventions

### General Principles
- **Max 100 lines per file** — split into focused, single-responsibility files if exceeded
- **No speculative features** — implement only what is explicitly asked
- **Minimal comments** — only document the WHY if non-obvious; code should be self-explanatory

### PowerShell Scripts
- **Function naming** — PascalCase (`Invoke-Whisper`), local variables camelCase (`$baseName`)
- **Full cmdlet names** — never aliases (`Get-ChildItem` not `ls`, `Where-Object` not `?`)
- **-LiteralPath for file operations** — mandatory when handling `videos/` paths (spaces, commas, etc.)
- **Type hints on parameters** — e.g., `[string[]]` for arrays
- **Group logic into small functions** — each function should have a single responsibility

### Docker
- **Pin base image tags** — e.g., `python:3.12-slim`, not `python:3.12`
- **One logical step per RUN layer** — chain with `&&` to minimize image layers
- **apt-get always uses --no-install-recommends**
- **Never run as root** — add a non-root user for production
- **Use .dockerignore** — exclude build artifacts and secrets
- **Multi-stage builds when appropriate** — don't include build tools in final image

### Python (if added)
- **PEP 8 style** — 4-space indentation
- **Type hints on all function signatures**
- **Specific exception handling** — never bare `except` clauses

## Project-Specific Rules

### Whisper Configuration
- **Default model is `turbo`** — only switch to `large-v3` if accuracy testing proves necessary
- **Output structure** — always use `--output_dir /app/output` to separate results from source
- **Filename escaping for ffmpeg** — escape `,` and `:` in `-vf subtitles=` syntax
- **WMV frame warnings are non-fatal** — use `-fflags +discardcorrupt -err_detect ignore_err`

### File Handling
- **videos/ directory** — only place source videos here
- **videos/output/ is read-only** — never edit or delete outputs programmatically (user-managed)
- **Skip already-processed files** — check for existing SRT/MP4 before submitting to Docker
- **Use -LiteralPath in PowerShell** — handles spaces and special characters in video filenames

### Docker Workflow
- **Run `docker compose --profile gpu build --no-cache`** when Dockerfile changes
- **Default profile is gpu** — CPU is explicit opt-in via `--profile cpu`
- **Models are persisted** — changes in `models/` volume apply across runs

## Task Guidance

### When Modifying PowerShell Scripts
1. Verify syntax with `-LiteralPath` for all file references
2. Test with sample filenames containing spaces/special chars
3. Ensure no aliases are used
4. Keep functions focused and under 30 lines if possible

### When Updating Dockerfile
1. Check that base image tag is pinned
2. Verify --no-install-recommends on all apt commands
3. Confirm non-root user is added if layers copy files
4. Run `docker compose --profile gpu build --no-cache` after changes

### When Adding Features
1. Check existing patterns in `.ps1` and `Dockerfile` first
2. Do not add commented-out code or TODOs
3. If new logic exceeds 100 lines, split into separate file
4. Test end-to-end: build → process sample video → verify output
